Security

Built to be trusted — and honest about the limits.

OpenFirst runs entirely on your device and hands your loved ones a single file they open offline. Here's what that protects, what it deliberately doesn't, and how you can check every claim yourself. The full threat model lives in SECURITY.md.

The four principles

  • Local-first, no server. There is no backend. The app is static files. Nothing you type is uploaded, because there is nowhere to upload it to.
  • A map, not a vault. The plan records where secrets live and how to find them — never the seeds, passwords, or PINs themselves. The app won't even let you store a raw secret, and strips any an older file tries to carry.
  • Outlives the company. Every export is an open, documented format — plain JSON + Markdown + files, or one self-contained HTML — readable and decryptable with standard tools in 20 years, with no OpenFirst in the loop.
  • Verifiable. The whole app is open source and builds to one auditable file.

What is protected

Provably offline

The built app ships a strict Content-Security-Policy with connect-src 'none'. Even a maliciously crafted package cannot make the reader phone home — the browser forbids every network connection. All code, fonts, and styles are inlined; nothing is ever fetched.

Strong, standard encryption

Password-protected exports use AES-256-GCM with a key derived by PBKDF2-HMAC-SHA256 at 600,000 iterations (OWASP 2023 guidance), random salt and IV per file. Every parameter is stored in the file, so it can be decrypted without OpenFirst — the recipe is public.

Entropy is the real lever. The app generates and nudges you toward a 6-word passphrase (~77 bits), which makes brute force infeasible. A short PIN does not — treat it as friction, not protection.

The visible password hint is tamper-evident: it's cryptographically bound to the file, so nobody can rewrite it (say, into a phishing instruction for a grieving heir) without breaking decryption.

Encrypt the draft too

While you build, the auto-saved draft can be encrypted at rest with a passphrase (Settings → Draft protection) — the plan and its files — with the key held in memory only. This protects a copied disk, profile, or backup.

Safe rendering

Guide text is rendered by a small, hand-written Markdown renderer that escapes all HTML and emits only a fixed set of safe tags. A tampered package cannot inject scripts or dangerous links.

What is not protected — please read

Your unlocked device. OpenFirst can't protect you from malware, a malicious browser extension, or someone at your unlocked screen while you edit. Draft encryption protects copies at rest, not a live-compromised browser.

Don't store secrets in the plan. No seeds, private keys, passwords, or PINs — even in notes. Keep them on hardware, paper, or a password manager and point to them.

A lost passphrase is unrecoverable. No reset, no backdoor — that's the point. Keep your durable encrypted export somewhere safe.

Discovery and delivery are yours. OpenFirst can't make your heir find the plan or receive the password. That's a human, out-of-band step — a sealed letter, a lawyer, split among relatives.

Verify it yourself

  1. Read the source. It's small and dependency-light — one runtime dependency for zip, everything else native Web Crypto.
  2. Reproduce the build and open dist/index.html from disk with your network set to offline. It works, because it never needed the network.
  3. Inspect an encrypted export. It's JSON — you can see the algorithm, KDF, iterations, salt, and IV, and decrypt it with the standalone recipe using only Node.js or Web Crypto.
  4. Watch the network with devtools open: loading a heir reader makes zero requests.

Report a vulnerability

Found something? Email security@openfirst.io with steps to reproduce, and please give us time to fix it before disclosing publicly. We'll credit you unless you'd rather we didn't.
